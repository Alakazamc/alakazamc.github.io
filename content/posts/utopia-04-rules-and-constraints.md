# 两种规则：关系声明与业务条件

| 环节 | 例子与含义 |
| --- | --- |
| 类型化物化 | 把“张三负责A项目”按已确定映射整理成“A项目→负责人→张三”；统一表达方式。 |
| 本体规则推理 | 本体明确某关系具有传递性，才允许沿该关系推出跨越中间对象的结论。 |
| 业务规则推理 | A项目评分85，满足明确规则“评分≥80→高风险”，得到新的高风险结论。 |

本体是统一的类别、关系及约束定义。传递性意味着“A与B有某关系，B与C有同一关系，则A与C也有该关系”。它需要业务上成立并明确声明，不能套到所有关系。

直属主管不能随意传递

```text
张三的直属主管是王五
王五的直属主管是赵六
不能推出：张三的直属主管是赵六
```

Utopia支持本体中的传递、对称、反向和子关系声明，也支持单个对象的属性条件、比较及受限计算。实际代码还支持沿一条明确连接边读取另一对象的属性并推出关系；这种受限一跳规则，不等于任意路径、聚合或任意SQL都能执行。

一个代码能表达的教学例子是：张三已有“直属主管→王五”这条边；若人明确配置“张三培训分低于60，王五培训分至少80，则张三需王五辅导”，系统可读取两人的分数，推出已定义的“需辅导”关系。原连接边和两项分数都要进入前提；不能因为两人名字相近就建立连接。

> ❗
> 规则需要明确配置或本体声明。模型读到“张三的主管是王五”，不能临场发明“主管就是项目负责人”。同样，没有审批属性不等于未审批；条件缺数据时应不产生该结论。

# 结论的时间、证明与失效

- 前提必须同时成立。交集就是共同覆盖的时间。例如两个条件分别在3月和4月成立，没有重叠，就不能合起来推一个同时成立的结论。

- 结论要有证明。证明树把“用了哪条规则、哪些事实、事实来自哪段原文”逐层串起来。结论还可能成为下一条规则的前提，但推理有深度和数量上限。

- 重算维护依赖。推理运行时重新计算当前应有的结论；不再成立的派生结论被标记失效。若A项目评分经核验改成70，要检查“高风险”是否仍有其他有效前提，而非永远保留第一次结果。

- 约束负责找问题。“同一项目同期只能有一个负责人”用于发现冲突，不是用来凭空选张三或李四。推导结论与已有断言冲突时，会被拦下并记录问题。

这里的断言是文档或人工直接给出的事实，派生是按规则计算的结论。实现优先保留断言，冲突的派生不能直接覆盖它；两个派生互相冲突时，也不能简单挑最新一个。这种优先顺序用于控制影响，并不证明断言一定真实，冲突仍需回到证据和规则审核。

# 从85分到70分：哪些内容应该变化

| 发生什么 | 该怎样理解 |
| --- | --- |
| 收到评分85的报告 | 保留评分事实、文档证据和适用时间；阈值规则满足时产生高风险结论。 |
| 后来报告把同一评分更正为70 | 先核验并应用更正，不能只因上传较晚就认定85错误；也要确认它不是另一日期的新评分。 |
| 推理任务再次运行 | 重新计算本库当前应有结论；旧评分前提失效后，检查高风险是否仍由其他有效前提支持。 |
| 没有其他支持 | 旧派生结论标记失效并保留记录；不能把新评分当作旧结论当时的依据。外部接口不承诺完整的历史证明快照。 |

- 别把未命中当作否定。评分70没有命中“至少80”，只说明这条规则没有推出高风险；若还存在其他风险规则，仍要分别检查。缺分数、计算失败与确实低于阈值也不是同一件事。

- 别把推理当作业务执行。推出高风险不自动等于冻结A项目、给王五发通知。执行动作还需要明确流程及权限。

- 读源码看三处。条件如何选取事实、前提区间怎样求交、重算如何对比应有与现有结论。再沿证明树查看规则和原文，就能判断一次结论变化是前提变了，还是规则变了。

> ✅
> 自测1：85分能自动变成高风险吗？答案：要先有适用的阈值规则。自测2：没找到审批记录能判未审批吗？答案：不能。自测3：两个前提时间不重叠怎么办？答案：不把它们合成同期结论。
