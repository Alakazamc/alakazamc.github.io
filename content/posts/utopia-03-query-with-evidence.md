# 按对象逐步查，按时间一起查

1. 找起点。用find_entities，即查找实体，搜索“A项目”。若出现多个同名项目，要结合类别、说明和事实确认对象；稳妥做法是选定UUID，即系统内部的稳定对象编号。
2. 查第一段关系。用entity_facts读取A项目的事实，或用neighbors查看直接相邻对象，按“负责人”关系找到张三，继续使用张三的编号。
3. 查第二段关系。读取张三的“直属主管”，找到王五。终点原先未知时，逐步寻找比预先猜一个王五再搜路径更符合问题。

两步现有关系回答一个问题

```text
A项目 → 负责人 → 张三 → 直属主管 → 王五
能回答：A项目负责人的主管是王五
不能推出：王五也是A项目负责人
```

这里不能推出负责人，根本原因是“主管”和“负责人”含义不同；人员后来可能变化是额外的时间问题。每一跳还要同时检查：这段关系在所问业务日期是否成立，以及系统在所问记录日期是否已持有它。

关系型数据库同样能表达这条链：把项目、负责人、员工汇报关系分别放在表里，再用SQL JOIN，也就是按共同编号连接表，也能找出王五。知识图谱的价值在于统一对象、关系含义和证据；它不要求底层必须换成专门的图数据库。

| 时间条件 | 回答什么 |
| --- | --- |
| at：世界时间 | 3月20日实际由谁负责，谁是当时的主管？ |
| as_of：记录时间 | 按系统4月1日的认知，怎样回答上述问题？ |

每一步都问同一个时刻

```text
3月20日：A项目负责人是张三；张三主管是王五。
4月1日：李四接任A项目；张三转向另一主管。
查3月20日时，两段关系都使用at＝3月20日，
不能接上张三4月以后的新主管。
```

如果4月10日才接受一项对3月事实的更正，“按现在知道的信息回看3月20日”与“按4月1日的认知回看3月20日”可能不同。因此两跳查询除了统一世界时间，也要统一记录时间，防止一半使用旧认知、一半使用新认知。

> ❗
> 各跳要使用相同的at和as_of，避免把不同年代的关系接在一起。当前快照中，省略as_of表示当前记录；省略at表示不过滤世界时刻，不会自动变成“只查今天”。

# 路径有边界，答案要有出处

paths_between用于“两端已经知道，想看怎样连上”的问题。它在实体之间的现有边上最多找三跳，搜索可从两种方向经过边，但关系原来的方向仍需解释。它不按业务含义限定每一步，不能把任意连接链当成负责人或审批关系。

- 注意读取层次。路径查询可能经过保留原文用词的开放陈述，不读取单独保存的派生结论；entity_facts则也能显示规则产生的结论。不同工具的结果范围不完全相同。

- 核对引证。聊天中的事实可带编号跳到证据原句。MCP是外部应用调用工具的接口，部分工具提供对象或事实编号及文档来源；路径等工具当前主要返回文本，不带聊天的引文编号。推理结论还要区分规则依据与原文陈述。

- 谨慎解释空结果。可能尚未接入文档、认错对象、时间过滤排除了关系，或搜索受数量与跳数上限影响。应说“在当前范围未找到”，而非直接断言不存在。

# 模型负责理解，工具负责读取

- 先理解问题再选工具。模型把“负责人的主管”拆成两段关系，并判断要补问哪个时间；工具按对象编号和条件读取数据。工具返回排序第一的同名对象，并不等于该对象一定正确，仍要看说明和其他候选。

- 把答案范围说清楚。有依据时回答“按目前记录，3月20日负责人的主管是王五”；资料不足时指出缺哪一段。回答不能补出工具没读到的关系，也不应把工具超限截断当作已经搜完全部知识。

- 读源码抓住输入和边界。先看实体参数如何解析、at与as_of怎样传入，再看结果属于事实还是派生、是否限额或截断，最后看证据怎样登记。这样比只找一个叫“查询”的函数更容易理解答案从哪里来。

> ✅
> 自测1：不知道主管名字时先调用两端路径搜索吗？答案：先从A项目逐跳查。自测2：查到王五主管张三，能说王五负责A项目吗？答案：不能，关系含义不同。自测3：空结果证明现实没有这条关系吗？答案：不能，先检查资料、对象、时间和查询限制。
