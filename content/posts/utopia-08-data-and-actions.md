# 从数据源到业务问题

1. 注册、授权、挂载：部署管理员注册数据源，授予工作区，再由知识库挂载。挂载时读取schema并形成可检索文档；schema来源跳过事实抽取，避免把列名抽成实体。
2. 解释业务口径：如风险字段risk_score究竟是0—100还是0—1，必须由定义说清。已确认映射会供聊天参考，拒绝的映射不会因重跑探索就自动变成已确认。
3. 查询而非断言：聊天在挂载数据源时可使用query_data，按来源方言执行单条只读SELECT/WITH，有行数限制和超时。不同引擎的只读保障不同，不能假定都有相同会话机制。
4. 分清入口：当前MCP没有暴露query_data；给外部Agent一个PAT，不会因此获得与内置聊天相同的数据库SQL工具。

> ❗
> 0036提出“表列对齐本体→规则→各方言SQL”的路线，完整表列绑定与渲染尚未完成。部分转换表达式已用于规则，不代表整条路线已实现。现有映射仍是可审核配置，不是知识账本里的事实。

- 0034的动作契约：部署级注册固定HTTP调用、声明标量参数并检查范围，授权给知识库，先预览再由人明确执行。它不是让模型编写任意脚本。

- 0050的尝试身份：一次用户操作应有稳定请求ID并绑定定义版本。请求可能已在对端生效但响应丢失，此时结果未知；重试发送可能重复扣款或建单，设计不自动重发。

- 当前状态：仓库尚未实现生产动作表、发送器和由规则自动触发外部动作的流程。HTTP收到202也只说明收到响应，不证明对端业务已经完成。

# 同一个风险问题的三种回答

| 你想问 | 应查什么 |
| --- | --- |
| A项目风险现在是多少 | 数据库当前记录或有来源的风险断言，并说明取数时刻。 |
| 为什么85算高风险 | 人声明的阈值规则“风险≥80”，以及实际读数85的依据。 |
| 高风险后是否建工单 | 这是对外副作用，需要独立动作授权与执行契约；当前仓库没有实现发送能力。 |

1. 先校口径：假设数据库列里是0.85，而文档写85分，先确认单位、刻度与计算规则。把0.85乘100换成85分是刻度转换；“达到80分算高风险”是业务判据，两者不能混在一个列名里。
2. 再核读数：查询成功只说明收到该次返回。还要看来源是否挂对、过滤条件是否只取A项目、结果是否截断，以及材料是不是把历史值当当前值。表结构可检索不代表模型写出的SQL一定符合业务口径。
3. 最后解释：给王五的回答可以说“按当前来源读得85，按已声明≥80规则为高风险”，并分别指出读数与规则。不要把一段流畅解释当作两类证据已经存在。

> ❗
> 动作设计里的“结果未知”有实际意义：例如工单系统已创建单据，Utopia却没收到响应。相同请求ID的再次提交应是同一次操作的回看；换一个ID是新的用户操作。这个设计约束不等于已实现对端恰好执行一次，也不能撤销远端已经发生的效果。

> 读这部分源码时，先找数据源授权与挂载，再找工具的开放集合和实际执行函数。读动作文档时则先看状态与实现位置，避免把提案中的表名当成数据库里已经存在的表。

# 自测与源码

1. 确认risk_score映射，就是确认风险85吗？答案：不是，前者说明计算方法；具体值仍需查询或有来源的断言。
2. 外部调用超时就一定没成功吗？答案：不是，应保留未知，不能据此自动重发。
3. MCP能直接调用query_data吗？答案：当前不能，内置聊天与MCP的工具集合不同。
