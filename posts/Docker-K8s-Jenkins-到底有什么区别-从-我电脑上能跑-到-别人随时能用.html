Docker、K8s、Jenkins 到底有什么区别？从“我电脑上能跑”到“别人随时能用”

2026-09-26

假设你写了一个 AI 问答程序。

输入问题，检索资料，调用模型，返回答案。你试了十几个问题，效果不错，便把代码发给同学，准备让他也体验一下。

过了一会儿，对方发来一张截图：报错了。

你问：“依赖装了吗？”

他说：“装了。”

你又问：“Python 版本对吗？”

他说：“我用最新的。”

你心里一沉：坏了，又得从配环境开始。

等你终于帮他把程序跑通，另一个想法冒了出来：为什么不把它放到服务器上，大家直接打开网页使用？这样就不用每个人都安装一遍了。

于是，你开始搜索“Python 项目如何部署”。

十分钟后，浏览器里打开了十几个页面，里面分别写着 Docker、Docker Compose、Kubernetes、Jenkins、Nginx、CI/CD。你本来只是想让别人用上自己的程序，现在却像是被要求先修建一座数据中心。

这些东西真的都要学吗？它们是不是在做同一件事？为什么有的教程只用 Docker，有的却把 K8s 和 Jenkins 全搬出来了？

问题的关键在于：“把程序部署起来”并不是一个动作，而是一连串不同的问题。这些工具，只是分别出现在了不同的环节。

把它们放回一个项目的成长过程里，就容易理解了。

代码写完了，但运行它的条件并没有跟着交出去

先回到最初那次报错。

你发给同学的，可能只是几个 Python 文件。但程序能在你的电脑上运行，依赖的不只是这些文件。还有 Python 解释器、第三方软件包、系统库、环境变量，以及你之前装过、现在已经记不清的软件。

这些东西共同构成了程序的运行条件。

所以，“代码完全一样，为什么结果不同”，有时候并不神秘：你们运行代码的环境根本不是一回事。

你当然可以写一份安装说明，告诉对方先安装什么，再执行什么。但说明越长，越容易遗漏。今天某个依赖发布了新版本，明天另一个安装包改变了行为，原来能成功的安装步骤，也未必一直产生相同结果。这也是为什么可重复的构建需要控制依赖与基础镜像版本，而不能只依赖一串没有固定版本的安装命令。

Docker 首先试图改善的，就是这种交付方式。

你不再只把代码交出去，而是把代码、运行时、依赖和默认启动配置组织成一个镜像。目标机器拿到镜像后，再按照指定的运行参数创建容器。

这里有几个名字，看起来相近，实际分工很清楚。

Dockerfile 是制作说明，镜像是制作出来的应用模板，容器是根据模板创建出来的实例。你可以用同一个镜像启动多个容器，就像同一份程序可以启动多次，但这些实例各有自己的运行状态。

而所谓“构建”，就是根据 Dockerfile 制作镜像；所谓“运行”，则是根据镜像创建并启动容器。这两件事发生在不同阶段。比如安装依赖，通常可以在构建镜像时完成，不需要每次启动服务都重新安装。

镜像制作好以后，还可以放进镜像仓库，让服务器下载。它和 Git 仓库不是一个东西：Git 仓库主要管理源代码，镜像仓库负责存储和分发容器镜像。

到这里，你交付给别人的就不再是“照着我的说明重新配一遍环境”，而是“使用这一份已经制作好的应用镜像”。

这就是 Docker 最容易让初学者感受到的价值：把原本散落在个人电脑和操作习惯里的运行条件，变成可以明确描述、重复制作和分发的东西。

不过，这里还有一个问题没讲清楚：容器究竟是什么？它为什么能做到这些？

Docker 打包的，不是一台完整的电脑

第一次接触容器，很容易把它理解成“小型虚拟机”。

这个比喻能帮助入门，但继续往下学时，就需要修正了。

在常见的 Linux 容器场景下，容器中的应用仍然是操作系统管理的进程。它并不是每次都启动一套完整、独立的操作系统。同一台 Linux 主机上的普通容器通常共享内核，而传统虚拟机一般有自己的客体操作系统内核。

为什么它们看起来又像彼此独立的小环境？

因为操作系统可以为进程提供隔离。Linux 的 namespaces 能让进程拥有相对独立的进程、网络等资源视图；cgroups 则负责资源统计和限制，例如控制一组进程使用的 CPU、内存等资源。

通俗地说，程序还是运行在这台机器上，但它看到的文件、网络和进程环境，可以经过专门安排。它不必直接面对宿主机上所有的软件和配置，也不必和另一个项目使用同一套依赖。

这就是为什么两个项目可以分别在自己的容器里，使用不同的软件环境。

也正因为它们仍然依赖底层操作系统和硬件，Docker 并不是“任何环境都能无条件运行”的魔法。尤其是 GPU 应用，宿主机仍需要满足驱动和容器运行支持的要求。镜像里装好了深度学习框架，并不能替代 NVIDIA 驱动及相应运行配置。

隔离也不等于绝对安全。给容器过大的权限，或者把宿主机的重要目录直接以可写方式交给它，仍然可能影响宿主机。容器提供了隔离机制，但隔离效果还取决于怎样使用它。

学到这里，做过 Python 项目的人通常会问：这和 Conda 有什么区别？我不是已经能创建独立环境了吗？

Conda 的重点是管理一套软件环境，包括 Python 版本、软件包，以及一些非 Python 依赖。Docker 还涉及应用镜像的制作与分发，以及容器的进程、网络和存储配置。两者存在交集，但目标并不相同，也可以一起使用。

对一个简单接口，我会倾向于少叠一层工具，直接使用合适的基础镜像安装依赖。对于复杂科研环境，在容器里继续使用 Conda，也完全可以是一种合理选择。

重要的不是站队，而是知道自己正在管理哪一层。

容器启动成功了，为什么网页还是打不开？

现在，假设你已经把 AI 问答程序放进容器，日志也显示启动成功。

你打开浏览器，却发现访问不了。

这通常是初学者第一次意识到：“程序正在运行”和“别人能够访问”，是两个问题。

一个网络服务需要监听某个地址和端口。端口可以粗略理解成一台机器上某项网络服务的入口。容器拥有自己的网络环境，因此应用在容器里监听了一个端口，并不意味着宿主机已经把它提供给外部访问。Docker 的端口发布，就是在这两层之间建立相应转发规则。

比如，应用在容器内监听 8000 端口，你可以让宿主机的 18000 端口转发过去。这样，外部访问的是宿主机的 18000，真正处理请求的程序却仍然在容器里的 8000 上等待。

两个端口不必相同。

还要注意监听地址。发布到 127.0.0.1，主要用于本机访问；发布到其他主机接口，则意味着不同的可达范围。不能为了省事，把数据库、管理后台和业务接口的端口全部不加区分地开放出去。

等你修好网络问题，同学终于用上了这个工具。过几天，你修改了代码，删除旧容器，重新创建一个新容器，准备发布新版本。

然后发现：用户之前上传的论文没了。

这又是另一个层次的问题。

容器在镜像之上拥有自己的可写层。如果上传文件只保存在那里，删除容器时，这一层也会随之删除。这里要区分“停止容器”和“删除容器”：停止并不会自动等同于销毁，但重新创建的容器也不会自动继承旧实例的可写层。

因此，重要数据通常需要放在独立存储中，再挂载给容器使用。Docker 管理的数据卷，就是让数据生命周期可以独立于容器的一种机制。

你可以换掉应用实例，但继续使用原来的数据。

这件事会逐渐改变你对服务器的理解。你不再把线上容器当成一台需要长期手工修补的电脑，而是把它当成一个可以根据镜像和配置重新创建的应用实例。新版本来了，制作新镜像、替换实例，比进去改几行文件、再祈祷自己没有漏记步骤，更容易形成可重复的交付过程。

不过，独立存储还不是备份。

用户误删了文件，磁盘损坏了，数据库内容被错误更新了，不能指望“数据卷”三个字替你撤销操作。持久化解决的是换容器后数据还在不在，备份与恢复解决的是原始数据出问题后怎么办。

你看，Docker 并没有让部署问题全部消失。它只是让其中一部分问题，有了更清楚、更统一的处理方式。

一个项目慢慢长大，Compose 就开始有用了

刚开始，你的问答程序可能只有一个后端。

后来，你想保存会话，于是增加数据库；想复用某些计算结果，于是加入缓存；想让用户提交论文后不用一直等待，于是把解析工作交给后台处理进程。

假设你决定这样设计：接口先接收任务并返回编号，后台进程继续解析论文，完成后把结果写入存储，用户再查询进度和结果。

这时，“启动项目”已经不只是启动一个 Python 程序了。

你需要同时安排几个服务：它们各自用哪个镜像，设置什么环境变量，通过什么地址联系，哪些目录保存数据。把这些全部写成零散的启动命令，过一阵子连自己也容易记不清。

Docker Compose 就是用一份配置描述这组服务，再统一管理它们。服务、网络、数据卷等关系可以写进 compose.yaml，之后通过 Compose 创建和更新应用。

这份文件的价值，不只是少敲几条命令。

它让项目的运行结构不再依赖口头交接。别人看到配置，就能知道这个项目除了后端，还需要哪些服务，怎样连接，数据放在哪里。

这里还有一个特别容易踩的坑：localhost。

在通常的独立容器网络中，后端容器里的 localhost 指向后端自己，不是旁边的数据库容器。在 Compose 默认网络里，服务可以通过服务名互相发现。假设数据库服务叫 db，后端就可以用这个名字寻找它，而不是把地址写成“我自己”。

这句话一旦真正理解，很多“明明数据库启动了，为什么连接不上”的错误就容易解释了。

另一个细节是启动顺序。数据库容器已经创建，不代表数据库已经完成初始化。Compose 可以结合健康检查和依赖条件，等待服务准备好之后再启动依赖方；应用自身仍然需要考虑连接失败和重试。

对于一个单机项目，做到这里，已经能形成相当清楚的部署方式。

这时没有必要因为听说 K8s 更强大，就急着把整个项目搬过去。Compose 和 K8s 并不是程序员水平的两个等级。前者能不能满足需求，取决于你要管理的系统，而不是它听起来够不够高级。

K8s 真正关心的，是“接下来还能不能保持这样”

假设项目继续发展，你开始把应用放到不同服务器上，并运行多个副本。

你很快会发现，新的麻烦不再是“怎么启动一个容器”，而是“这些容器应该放在哪里，接下来由谁持续照看”。

某个实例退出，需要补回来；某台机器不可用，需要考虑在其他机器上重新创建；新版本发布，需要逐步替换；用户请求也不能一直指向已经消失的旧实例。

Kubernetes，也就是 K8s，提供的正是集群中的应用调度和管理机制。集群由控制平面和工作节点等部分组成，工作节点承载应用运行。

理解它最重要的切入口，是期望状态。

手动操作时，你说的是：“帮我启动三个实例。”

使用 Kubernetes 时，你可以声明：“我希望这个应用保持三个副本。”

这两句话只差一点，背后的工作方式却不同。K8s 的控制器会持续观察实际状态，再采取动作，让实际状态接近期望状态。少了一个副本，就尝试补建；状态发生变化，就继续处理，而不是执行一次启动命令后就结束。

可以把它理解成恒温器。你设置的是目标温度，而不是亲自决定加热器每一分钟开还是关。

当然，恒温器不能凭空提供能源，K8s 也不能凭空创造硬件。它能做的是根据现有资源和配置进行调度，不是把不足的内存变出来。这个边界，决定了“具备自动管理机制”和“服务永远不会出问题”不是一回事。

在实际使用中，你最先碰到的通常是 Pod、Deployment 和 Service。

Pod 是 K8s 创建和管理应用运行的基本单位。它可以包含一个或多个紧密协作的容器，这些容器一起调度，并共享网络等资源。最常见的入门情形，是一个 Pod 里运行一个主要应用容器，但这不是“Pod 只能装一个容器”的规定。

Deployment 负责管理应用副本和更新。你在里面声明镜像版本、副本数量等要求，它再通过相关控制器维持这些实例。

Service 则提供相对稳定的访问方式。因为 Pod 可能被删除重建，地址可能变化，调用方不应该把某个临时实例的地址永久写死。Service 把“我要访问这个服务”和“它此刻具体有哪些实例”分开了。

于是，你不必每天手工追着每个实例的地址修改配置。

这些工作也不是一个程序全部包办。API Server 接收管理请求，控制器持续处理状态变化，Scheduler 为 Pod 选择节点，节点上的 kubelet 再协调容器运行。你使用的 kubectl，就是操作 Kubernetes API 的命令行工具之一。

到了 AI 服务，这套管理还会遇到一个很具体的问题：程序启动了，但模型可能还没加载完。

这时就需要区分“活着”和“准备好了”。K8s 的启动探针用于判断初始化是否完成，就绪探针判断现在能否接收请求，存活探针则用于识别某些需要重启的故障。就绪失败不等于一定重启；把这些检查混在一起，反而可能让正常加载模型的应用不断被重启。

类似地，滚动更新也不是一句“无缝上线”就能概括的。Deployment 可以按策略逐步替换副本，但新实例是否真正可用、旧实例能否妥善结束工作，还需要应用行为和配置配合。

K8s 提供的是一套持续管理应用的机制，而不是替开发者承担所有正确性。

代码有 Bug，换一个 Pod 仍然可能出错；三个副本各自把会话保存在内存里，也不会自动拥有一致的会话状态。独立进程通常不共享普通应用内存，这件事不会因为使用了集群就改变。

因此，学习 K8s 到一定程度，最终还是会回到应用设计本身。

Jenkins 出场时，解决的已经不是“容器怎么运行”

现在，我们暂时不管用户有多少，也不管服务器有几台。

只看你每次发布新版本时在做什么。

修改代码，获取代码，运行测试，构建镜像，上传仓库，更新服务，检查结果。

第一次，你小心翼翼地做完了。

第二次，你照着上次的记录又做了一遍。

到了第十次，你可能开始觉得：“这些步骤明明差不多，为什么每次都要我坐在这里操作？”

Jenkins 的价值，就出现在这里。

它可以把构建、测试、发布等操作组织成可触发、可执行、可记录的流水线。这些步骤可以写进 Jenkinsfile，和业务代码一起保存和评审。

比如，你可以设计一条这样的发布流程：

代码变更 ↓ 执行测试 ↓ 构建镜像 ↓ 上传镜像仓库 ↓ 发布到测试环境并验证 ↓ 审批后发布到正式环境

这是一种流程设计，不是所有项目必须采用的固定模板。重点在于，原来依赖手工完成的步骤，现在有了明确顺序和执行记录。

这也就说到了 CI/CD。

CI，也就是持续集成，强调频繁整合代码变更，并通过自动化构建和测试尽早发现问题。例如，提交一份代码后就运行检查，而不是等多人各自写完一大块功能，最后一起合并时才发现冲突和错误。

CD 则需要分清两个概念。持续交付意味着通过验证的版本已经处于可以发布的状态，正式发布可以保留人工审批；持续部署则进一步把符合条件的变更自动发布到生产环境，不要求每次人工批准。

因此，“公司有 CI/CD”并不等于“任何人一提交代码，就立刻修改线上服务”。

Jenkins 是实现这类流程的工具之一，不是 CI/CD 本身。

它内部也有分工：控制端负责协调和管理，执行端负责实际运行任务。你会看到 Agent 这个词，但这里的 Agent 指构建执行端，不是大模型智能体。执行端可以是一台机器，也可以使用相应的容器环境。Jenkins

执行端还需要具备真正干活的条件。测试 Python 项目，需要 Python 和测试依赖；构建镜像，需要镜像构建能力；更新服务器，需要对应权限。Jenkins 主要是在组织和调用这些工具，而不是安装完之后就自动拥有所有环境。

这里还有个很值得警惕的误解：流水线通过，不代表代码被某种权威认证为“绝对正确”。

它只是说明，你配置的步骤满足了相应成功条件。没有覆盖到的错误，不会因为页面上出现绿色对勾就自动消失。测试报告、命令结果和流水线规则，仍然要由项目自己设计。

对于 AI 项目，这点尤其明显。接口正常返回，并不意味着模型回答正确。我会建议在工程测试之外，再准备一小套固定的效果回归样本，至少能知道这次修改有没有明显损害检索或回答质量。

至于一定要不要学 Jenkins，我的看法是：CI/CD 的思路值得学，但工具不必只认一个。GitHub Actions 同样可以通过事件、工作流和执行节点组织自动化任务。理解流程以后，再换具体平台，比只记住某个网页上该点哪个按钮更有用。

最容易混淆的，其实是“发布路线”和“访问路线”

把前面的东西连起来，会出现两条不同的路线。

一条是你把新版本送到服务器上的路线。在这个项目里，可以设计成：

代码仓库 → Jenkins 测试与构建 → 镜像仓库 → Compose 或 K8s 更新应用。

另一条是用户使用服务的路线，例如：

浏览器 → 网络入口 → 应用 → 数据库或模型服务 → 返回结果。

前一条处理软件交付，后一条处理用户请求。

Jenkins 通常不需要夹在用户和应用之间。它完成发布以后，普通用户访问业务接口，并不需要先经过 Jenkins。这是从它的流水线职责中就能看出的区别。

而 Nginx 之类的反向代理，常常出现在第二条路线上。它接收请求，再根据配置转发给后端服务。比如同一个入口下，网页请求交给前端，接口请求交给 Python 后端。

所以，Docker、K8s、Jenkins 和 Nginx 并不是一组互相替代的软件。它们有时会配合，有时不需要全部出现，取决于你的架构。

这也解释了为什么“用 Docker 运行 Jenkins，再由 Jenkins 发布容器化应用”并不矛盾。

一个工具自身怎样运行，与它负责完成什么工作，是两回事。

至于最初那个问题——到底选谁部署——现在也可以换一种问法了：

应用环境准备怎样交付？一台机器是否够用？是否需要集群管理？发布过程有哪些重复步骤？用户请求从哪里进入？

问题分清，工具才选得清。

真正让服务稳定的，往往是那些不太显眼的基础

聊到这里，很容易产生一种错觉：把这几个工具装好，项目就算完成了工程化。

但真正遇到故障时，你会发现，决定排查速度的，常常是更基础的能力。

比如，服务打不开，你是否知道应该先看应用日志，还是检查端口发布？程序退出，你是否能判断是配置错误、资源不足，还是代码异常？用户说“今天特别慢”，你能不能找到时间究竟花在哪里？

日志、指标和链路追踪，就是为不同层次的观察服务的。日志记录具体事件，指标反映延迟和错误率等整体情况，链路追踪帮助观察一次请求经过多个组件的过程。

对于一个 AI 问答程序，我宁愿先看到几条有用的记录：检索用了多久，模型调用用了多久，哪个任务失败了，失败原因是什么，也不希望项目一开始就堆上一套复杂监控系统，却只记录一句“请求失败”。

数据也一样。

假设新版本改变了数据库结构，旧版本却还依赖原来的字段。此时把应用镜像换回去，并不能让被删除的字段和内容自动回来。这是一个很直接的逻辑结果：你替换的是应用，改变的却还有数据。

所以，我会把应用回滚、数据迁移和备份恢复分开设计。不能用一句“支持回滚”掩盖三个不同问题。

密钥和权限同样值得认真对待。数据库密码、模型 API 密钥，不应该为了方便就写进所有人都能获取的镜像。流水线能够调用生产环境凭据，也意味着它具有相应的访问能力，凭据的提供与使用范围需要受控。

再说回 AI 服务，模型副本也不是开得越多越好。独立进程可能分别加载模型，占用各自的内存；增加副本前，需要实际测量资源，而不是只盯着“并发数”往上调。

这些事情没有某个响亮的工具名字，却直接决定服务能否长期运行。

我认为，程序员学习部署最容易走偏的地方，就是把“已经使用某个工具”当成“相应问题已经解决”。

用了 Docker，不代表数据不会丢；用了 K8s，不代表应用永不故障；用了 Jenkins，也不代表每次发布都是正确的。

更有效的思路是反过来：先说清需要保证什么，再看由哪一层、哪一个机制负责。

对刚入门的人来说，不必一口气建完所有东西

我不建议第一次部署，就同时学习完整的集群、流水线、网关和监控平台。

这样做最大的问题，不只是复杂，而是出错时你很难判断错误发生在哪一层。应用没有写对、容器没有启动、网络没有连通、集群没有资源，都可能表现成同一句话：“打不开。”

更好的起点，是选一个自己已经理解的项目，把它真正交给别人使用。

先让它成为一个能够通过网络访问的服务，弄清启动命令、监听地址和日志。然后用 Docker 描述环境，亲手构建镜像，再尝试替换容器，确认数据应该怎样保存。

项目确实需要多个服务时，再用 Compose 把它们组织起来。等你已经知道手工发布的完整过程，再把这些经过验证的步骤写进流水线。最后，当多节点、多应用或团队的平台需求真实出现时，再进入 K8s。

这不是必须遵守的行业顺序，而是我更推荐的学习顺序：每引入一个工具，都能清楚地说出，它刚刚替我解决了哪个问题。

你甚至可以给自己设一个很朴素的目标：把项目交给另一个人，不通过语音陪他逐条操作，他也能根据项目文件把服务启动起来。更新一次版本后，重要数据还在；出了问题，你知道去哪里找证据。

这个目标听起来没有“搭建云原生平台”那么宏大，但完成它，往往意味着你已经真正理解了软件交付。

回到文章开头。

你本来只是写了一个能回答问题的程序，后来为了让别人使用，开始处理环境、网络、数据、更新和故障。Docker、Compose、K8s、Jenkins，就是在这些问题逐渐出现时，进入了你的工具箱。

它们不是必须集齐的一套装备，也不是简历上越多越好的缩写。

学会它们带来的变化，应该发生在一个更具体的时刻：有人告诉你“服务打不开了”，你不再只能重复一句“但我电脑上是好的”。

你知道当前运行的是哪一版，知道请求经过哪些地方，也知道该从哪里开始排查。

到这时，代码才不只是你曾经成功运行过的东西，而是一个你能够交付、维护，并让别人放心使用的服务。
